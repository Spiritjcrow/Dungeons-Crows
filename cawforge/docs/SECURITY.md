# CAW Forge security and fail-closed model · Genesis v0.1

**Boundaries:** Local Ed25519 private keys reside in mode 0700 state directory with 0600 key files. No actual blockchain wallet, real token, payout, network miner or background workload is created. Signed work receipts use versioned domain separation + genesis namespace + task ID + SHA-256 of coordinator-authorized job + result digest + random nonce + UTC timestamp + worker identity. The verifier pins the worker public key in local state, regenerates and checks exact output, and signs acceptance separately. SQLite PRIMARY KEY on `job_id` and UNIQUE ledger job IDs prohibit re-crediting in one local genesis. `BEGIN IMMEDIATE` serializes acceptance on one SQLite DB.

**Expected attacks and mitigations:** Edited output -> hash mismatch and reject. Edited receipt -> invalid worker signature. Forged complexity -> signed coordinator specification mismatch. Replay in same ledger -> accepted state and uniqueness check; replay in a second genesis -> genesis namespace mismatch. Unproductive cycles -> reject workloads not in coordinator policy; only fixed Dungeons & Crows map generation is enabled. Inflated quality -> quality and utility are verifier-assigned and require deterministic validation. Supply inflation -> simulated global cap check, no transfer route. SQLite tampering -> ledger hash-chain, signature check and recomputation detect ordinary editing.

**Important limitations:** `sha256` and Ed25519 signatures only authenticate data relative to trusted keys. If local adversary controls both keys and database, they can rewrite its history: periodically externally anchor signed ledger head digests. Local keys are not encrypted at rest, so protect account/device with OS permissions and backup encryption. Ed25519 is not necessarily available on all Android Python packaging builds. Receipt timestamp is a trace value, not proof of real elapsed compute. Reward “difficulty” is policy weight, not verified energy consumption or cryptographic hardness. Seeded maps are reproducible and can be copied; without approved task registration, uniqueness alone is insufficient for open mining. The same process can invoke both worker and verifier; separate keys alone are not organizational independence. This is **not** a consensus protocol.

**Controls needed before expansion:** Separate signer on tester device; independent commit-signing key ceremony; allowlist and signed coordinator work authorizations; quorum of reviewers; external hash checkpoint; stronger workload metrics; Sybil resistance; dispute and appeals procedure; privacy policy and retention; fairness regression suite; meaningful game engine integration; external security audit; regulatory/tax review; approval of any issuance schedule or contributor compensation.

**Rootless continuity:** Queue and outputs persist in SQLite; no service or fixed IP/SSID needed. A crash before transaction commit leaves `QUEUED` or `WORKED` state, so restart `work`/`verify` as appropriate. Database uses atomic transactions. WAL sidecars may exist, so include all SQLite files in encrypted backups after stopping writers or use SQLite backup API. Never expose the private `.pem` files.

**Rollback:** Stop writers. Preserve and hash a forensic snapshot of `genesis.sqlite3` and its WAL/SHM sidecars. Restore from a verified prior backup; rerun `audit` before resuming. Do not delete a rejected receipt or manipulate balance records to “fix” a discrepancy. Do not rotate keys silently; a separate explicit migration procedure is needed.

**Threat-model scope:** This release handles accidental corruption and unsophisticated fraud at one host. It does *not* provide protection against malicious OS administrators, collusion, key theft, distributed consensus attacks, ransomware, quantum attackers, or compromised Python dependencies.
